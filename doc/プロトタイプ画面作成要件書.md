# Re:Tailor プロトタイプ画面作成要件書

## 1. 目的

`doc` フォルダ内の企画資料・サイトマップ・画面設計書を基準に、今後追加するプロトタイプ画面の品質をそろえる。特に次の2点を必須とする。

- Re:Tailor 全体でデザインと操作感を統一する
- 主要な操作から実際に次の画面へ遷移でき、ひとつのサイトとして確認できるようにする

本書は、画面の実装前に確認する作成ルールと受け入れ条件を定めるものである。

## 2. 参照資料と実装場所

### 2.1 参照する資料

優先順位は次のとおりとする。

1. 最新の企画書・画面設計書
2. 最新のサイトマップ
3. テーブル定義書・外部 IF 仕様書（入力項目、表示項目、状態の確認）
4. 既存のプロトタイプ画面

資料間で内容が異なる場合は、勝手に決めず、画面作成前に差分を記録して確認する。

### 2.2 ファイルの配置

- HTML: `プロトタイプ/templates/`
- CSS: `プロトタイプ/static/`
- JavaScript: `プロトタイプ/static/`
- 画面仕様・確認記録: `doc/`
- 画像などの素材: `プロトタイプ/` 配下の既存配置に合わせる

新しい画面を作る場合は、ファイル名を画面設計書・サイトマップ上の画面名と対応させる。日本語ファイル名を増やす場合は、既存の命名との一貫性とリンク切れがないことを確認する。

## 3. 画面作成前の必須確認

各画面の実装開始前に、次の内容を 1 画面 1 枚の簡易仕様として整理する。

- 画面 ID、画面名、画面の目的
- 利用者（未ログイン、ログイン済み、出品者など）
- 参照するサイトマップ上の位置
- 画面へ入る遷移元
- 画面から出る遷移先
- 主操作（購入、出品、保存、送信など）
- 戻る操作・キャンセル操作の遷移先
- 必須入力、入力形式、エラー表示
- 表示する仮データ、空データ、完了状態
- デスクトップでの表示幅とレスポンシブ対応範囲

画面設計書にない要素を追加する場合は、目的と遷移先を明記する。見た目だけのボタンやリンクは作らない。

## 4. デザイン統一要件

### 4.1 ブランドと基本トーン

- サービス名は `Re:Tailor` と表記し、表記ゆれを作らない。
- 「誰かの手から誰かの手へ渡る」というサービスの温度感を保ち、過度に装飾的な画面にしない。
- 既存画面の白、黒・濃いグレー、オリーブ系のアクセントを基本とする。
- 画面単位で独自の色体系、フォント体系、ボタン形状を新設しない。
- 背景色、本文色、補助文字色、罫線色、アクセント色は CSS 変数または共通クラスで管理する。

### 4.2 タイポグラフィ

- 日本語本文は既存画面で使用している日本語フォントの指定を優先する。
- 英字ロゴや見出しのフォントを変更する場合は、サイト全体への影響を確認する。
- 見出し、本文、補助説明、ラベル、エラーメッセージのサイズと太さを役割ごとにそろえる。
- 長い日本語が折り返されても、ボタン・入力欄・カードの高さが不自然に崩れないようにする。

### 4.3 レイアウト

- ヘッダー、ロゴ、戻る操作、主要コンテンツ、フッターの位置関係を既存画面に合わせる。
- コンテンツ幅、左右余白、セクション間隔、入力欄の高さを既存画面から流用する。
- フォーム画面では、ラベル、必須表示、入力欄、補足、エラーの順序を統一する。
- 一覧画面では、項目の並び順、画像比率、価格表示、状態表示、操作ボタンの位置をそろえる。
- 主要操作は画面内で 1 つに絞り、主ボタンと補助ボタンの見た目を区別する。
- デスクトップ幅での確認を基本とし、狭い幅でも横スクロールや要素の重なりが発生しないことを確認する。

### 4.4 共通部品

必要に応じて次の部品を既存画面から再利用する。

- ヘッダー、ロゴ、メニュー、カート・アカウント導線
- 戻るボタン、キャンセルリンク
- 主ボタン、補助ボタン、危険操作ボタン
- 入力欄、セレクト、チェックボックス、エラーメッセージ
- 商品カード、一覧行、価格・状態表示
- 確認画面、完了表示、空データ表示

同じ意味の操作に別の文言を使わない。例として、登録を確定する操作は画面間で「登録する」または合意した文言に統一する。

## 5. 画面遷移要件

### 5.1 基本ルール

- サイトマップに存在する画面は、少なくとも 1 つの入口から到達できるようにする。
- ヘッダー、メニュー、カード、ボタン、リンクなど、クリック可能な要素には明確な遷移先を設定する。
- 仮実装でサーバー処理を行わない場合も、次に確認したい画面へ HTML リンクまたは JavaScript で遷移させる。
- 遷移先が未実装の場合に `#` を残さず、未実装であることを仕様書に記録する。
- `href` と `onclick` を同じ要素に重複して設定しない。
- フォーム送信は、送信後に表示する確認画面または完了画面まで遷移を定義する。
- 戻る、キャンセル、閉じる、ロゴ、ブラウザバックの挙動を画面ごとに確認する。
- 破棄、取り下げ、削除などの不可逆操作には確認画面または確認ダイアログを設ける。

### 5.2 現在の主要導線

追加画面は、次の既存導線を壊さないこと。

| 起点 | 操作 | 遷移先 |
| --- | --- | --- |
| `top-index.html` | カートアイコン・カート商品 | `buy.html` |
| `top-index.html` | 商品を出品 | `syuppin_itiran.html` |
| `top-index.html` | サインイン | `signup.html` または `login.html` |
| `login.html` | ログイン | `top-index.html`（現状の仮遷移） |
| `login.html` | サインアップ | `signup.html` |
| `syuppin_itiran.html` | 出品 | `syuppin.html` |
| `syuppin_itiran.html` | 編集 | `naiyouhensyuu.html` |
| `syuppin_itiran.html` | 取り下げ | `torisage.html` |
| `syuppin.html` | 出品する | `syuppin_itiran.html`（現状の仮遷移） |
| `buy.html` | 購入手続き | `confirm.html` |
| `confirm.html` | 戻る・内容変更 | `buy.html` |

この表に新しい画面を追加し、起点・操作・遷移先・戻り先を必ず記録する。既存の `#`、空リンク、存在しないファイルへのリンクは画面確認前に解消する。

### 5.3 遷移状態

各画面について、最低限次の状態を用意する。

- 初期表示
- 入力中または選択中
- 入力エラー
- 確認
- 完了
- データがない場合
- 読み込み失敗または対象が存在しない場合（必要な画面のみ）

プロトタイプでは実データ連携を行わなくてもよいが、状態を確認できる仮データまたは固定表示を用意する。

## 6. HTML・CSS・JavaScript 要件

- HTML は `templates`、CSS と JavaScript は `static` に置く。
- 既存の相対パス規則 `../static/` と `templates` 間のリンク規則を維持する。
- ページ固有のスタイルはページ用 CSS にまとめ、他画面の既存スタイルを不用意に上書きしない。
- 反対に、複数画面で使うスタイルは共通化を検討し、同じ値のコピーを増やさない。
- JavaScript で表示を変更する要素には、初期表示でも破綻しない HTML を用意する。
- ボタンは役割に合った `type` を指定し、リンクはリンク、処理はボタンとして使い分ける。
- 画像には内容を示す `alt` を付け、装飾画像は空の `alt` にする。
- 入力欄には対応する `label`、`id`、`name` を設定する。
- アイコンだけのボタンには `aria-label` または画面上で確認できるラベルを付ける。
- 外部フォント・画像・外部サービスに依存する場合は、利用できない場合の表示も確認する。

## 7. 受け入れチェックリスト

### デザイン

- [ ] 既存画面とロゴ、色、フォント、余白、ボタン形状が統一されている
- [ ] 主操作が一目で分かり、補助操作と区別されている
- [ ] 日本語の折り返し、長い文言、エラー表示でレイアウトが崩れない
- [ ] デスクトップ表示で要素の重なり、横スクロール、意図しない空白がない
- [ ] 画像、アイコン、入力欄に必要な代替テキスト・ラベルがある

### 遷移

- [ ] サイトマップ上の入口から新画面へ到達できる
- [ ] 新画面の主操作が確認画面または完了画面までつながっている
- [ ] 戻る、キャンセル、閉じる、ロゴの遷移先が想定どおりである
- [ ] `#` のみの仮リンク、リンク切れ、存在しないファイルへのリンクがない
- [ ] ブラウザで直接開いた場合も CSS、JavaScript、画像の相対パスが解決する
- [ ] 未ログイン・ログイン済みなど、利用者状態に応じた入口を確認している

### 動作

- [ ] 必須入力を空にした場合の表示を確認できる
- [ ] 正常入力から確認・完了まで操作できる
- [ ] キーボード操作とフォーカス位置が確認できる
- [ ] 画面の主要操作を一通り実行してコンソールエラーがない
- [ ] 変更した HTML、CSS、JavaScript のファイル名と遷移表を更新している

## 8. 作業手順

1. 企画書・サイトマップ・画面設計書から対象画面と遷移を確定する。
2. 本書の「画面作成前の必須確認」を埋める。
3. 既存画面から共通部品とデザイン値を選ぶ。
4. HTML を作成し、入口・主操作・戻る先を先に接続する。
5. CSS と JavaScript を追加し、正常系・エラー系・空状態を確認できるようにする。
6. 「受け入れチェックリスト」を実行する。
7. 必要な画面リンクと仕様書を更新し、確認対象を共有する。

## 9. 追加提案

今後の画面数が増える前に、次の整備を推奨する。

- 共通の CSS 変数とボタン・フォーム部品をまとめたスタイルを作る
- 画面 ID、ファイル名、入口、遷移先を一覧化した遷移管理表を作る
- `#`、`javascript:history.back()`、存在しない HTML リンクを定期的に点検する
- ヘッダーのアカウント、通知、検索など未接続の操作について、遷移先画面をサイトマップに追加する
- 商品詳細、購入完了、ログアウト、パスワード再設定など、主要導線上で不足している画面を優先順位付きで整理する
